# M1 — the video spike

`DESIGN.md` section 13 makes M1 a go/no-go gate, and it gates two things:

1. **Two 16 KB video pages under DOS on a 128 KB PCjr.** If this does not
   work, page flipping is not free, every frame needs a buffer copy, and the
   pipeline in section 7 has to be redesigned. Section 14 rates it the
   highest-severity risk in the project.
2. **Memory throughput.** Section 2's table — ~680 KB/s filling, 217–290 KB/s
   copying — is *analytical*. It was derived from the six-clock bus cycle in
   the PCjr Technical Reference and has never been measured. Section 7's entire
   frame budget is built on it.

So M1 does three things and stops: sets up mode 8 with two pages, flips them at
vertical retrace with visibly different content, and times the fill and copy
primitives with Abrash's Zen timer.

## Getting the tools

Nothing here needs a licence or a subscription.

**Open Watcom C/C++ V2.** The maintained fork, not the 1.9 release from 2010.
Windows installer from <https://github.com/open-watcom/open-watcom-v2/releases>
(`open-watcom-2_0-c-win-x64.exe`, or the `-x86` build). Let it set the
environment variables, or run `owsetenv.bat` from the install directory in the
shell you build from. Check it with:

```
wcc -?
wlink
wmake -?
```

Brutman's mTCP is built with Watcom and supports the PCjr, so this toolchain is
known to produce working PCjr binaries.

**NASM.** <https://www.nasm.us/> — the Windows installer, or just drop
`nasm.exe` anywhere and pass its path to the build. Josh Foster's
`pcjr-asm-game` Makefile expects it at `%LOCALAPPDATA%\bin\NASM\nasm.exe`; that
path does not exist in this checkout, so either install it there or override:

```
wmake NASM=C:\path\to\nasm.exe
```

**DOSBox-X.** <https://dosbox-x.com/> — needed rather than plain DOSBox
because `machine=pcjr` is better supported there, and because plain DOSBox
cannot be configured down to 128 KB.

## Building

```
wmake                     # -> build\m1.exe
wmake clean
```

or, if `wmake` is the thing that is missing or misbehaving:

```
build.bat
```

`build.bat` runs the same three commands in the open and checks for each tool
before starting, which makes it the better one to reach for when something is
wrong.

Both produce `build\m1.exe` plus NASM listings (`build\*.lst`) and a link map
(`build\m1.map`). The listings are worth keeping: this code cannot be run on
the machine it is written on, so reading the generated instruction stream is
the only review available before it reaches hardware.

## Running

In DOSBox-X:

```
wmake run                 # 128 KB PCjr -- the configuration that matters
wmake run-dev             # PCjr with a memory sidecar, for quick iteration
```

On real hardware, copy `build\m1.exe` to a floppy or CF card and run it. To
capture the numbers rather than read them off the screen:

```
M1 /batch > M1.LOG
```

The report is 80 columns wide. A PCjr that booted into 40-column text will wrap
it, so either redirect to a file or run `MODE CO80` first.

### Options

| Option | Effect |
|---|---|
| `/nobench` | skip the timing runs |
| `/noflip` | skip the visual page-flip test |
| `/bios` | flip pages with `int 10h AX=0583h` instead of `OUT` to `0x3DF` |
| `/batch` | never wait for a keypress |
| `/reps=N` | timed repetitions per primitive, default 8 |
| `/pa=N` `/pb=N` | force the two 16 KB page numbers |
| `/force` | run even where the BIOS model byte is not a PCjr's |

`/force` exists for emulator experiments and is genuinely unsafe anywhere
else: M1 writes to fixed physical addresses in the low 128 KB on the strength
of a page register only the PCjr has, and on any other machine those bytes
belong to DOS. Without `/force` the program checks `F000:FFFE` for `0xFD` and
refuses.

## What the program does, and why each part is there

### Source layout

```
src/pcjr.h           declarations and mode 8 constants
src/m1.c             the driver: memory map, verification, visual test,
                     benchmark harness, report
src/asm/pztimer.asm  Abrash's precision Zen timer, adapted to a segmented .EXE
src/asm/pcjrvid.asm  mode set, page register, palette, retrace waits
src/asm/prims.asm    fill_words / fill_bytes / copy_words / copy_bytes /
                     fill_rect_m8 / fill_band_m8
src/asm/dosmem.asm   DOS memory enquiry and allocation, far peek and poke
makefile             wmake build
build.bat            the same build without wmake
conf/                DOSBox-X configurations
```

The split follows section 12: logic in C, and only the routines where the
cycles actually live in assembly.

### 1. Where is the memory?

M1 does not assume the plan in section 3 works. It reports:

- `int 12h` memory size, and what it means. A 128 KB PCjr should say **112 KB**,
  the missing 16 KB being the video page BIOS kept for itself.
- The whole DOS memory arena, walked through the MCB chain
  (`int 21h AH=52h`), block by block, with each block's physical span and
  whether we own it. This is the diagnostic that turns "can we get page 6?"
  into something you can read off a screen.
- Which of the eight 16 KB pages are ours: claimed from DOS, or sitting above
  the arena entirely and therefore part of BIOS's video reserve.

Then it claims the largest free block DOS will give up and picks the highest
two usable pages — pages 6 and 7 on the machine section 3 describes, which
leaves the bottom 96 KB contiguous.

### 2. Verification, before anything is built on top

Three checks, all done in mode 8, all reported as pass or fail:

- **The two pages are distinct RAM.** Signatures written to the first and last
  word of each page and read back. On a machine where the address decode wraps,
  both "pages" would be the same memory, and the flip would appear to work
  while doing nothing at all.
- **The B8000 window follows the CPU page field.** Section 3 states as fact
  that the PCjr has no separate video RAM and that `B800:0000` is a window onto
  whichever 16 KB block the CPU page field selects. M1 writes through the
  window, reads back from the physical address, and then does it the other way
  round.
- **Which of `BH` and `BL` `int 10h AX=0583h` wants as the CPU page.** Section 3
  says `BX = (cpu << 8) | crt`. Flashparty's `set_vid_160_100_16` implies the
  opposite, and Ralf Brown agrees with Flashparty. Rather than pick a side, M1
  puts a distinct signature in each page, asks BIOS for a specific pairing, and
  reports which one turned up in the window.

If any of the first two fails, M1 stops and says NO-GO, because the benchmarks
below would otherwise be measuring something other than what they claim.

### 3. The visual test

Two phases, and the second is the interesting one.

**Page identity.** Each page gets a different HUD-band colour and a white block
at a different height; the CRT page field swaps twice a second. If flipping is
not working, the screen simply will not change.

**Smooth motion.** Identical backgrounds on both pages, and a white bar swept
left and right — redrawn into the back page every frame, with its previous
position restored from the band model first. That is a one-object version of
the per-buffer dirty-rect pipeline in section 7, and it is what tearing and
missed retraces show up in: a seam across the bar means the flip landed outside
blanking, and a strobe means a frame was missed.

Both phases paint the sky, mountain strip and ground as flat horizontal bands
in the section 5 palette indices. That is not decoration. A solid horizontal
band is scroll-invariant, which is the observation section 7's whole budget
rests on, so it is the right thing for the spike to be drawing.

### 4. The benchmarks

Nine primitives, timed with the Zen timer, interrupts disabled, the display
active in mode 8 and the writes going to the page the CRTC is not showing —
which is the situation the renderer will actually be in.

| What | Why it is in the list |
|---|---|
| `rep stosw` → video via `B8000` | section 2's fill figure, through the window |
| `rep stosw` → video, direct segment | the same fill addressed as plain RAM. Identical on paper; a difference would be very interesting |
| `rep stosw` → plain RAM | the same fill somewhere the video gate array is not fetching from, which isolates contention from instruction cost |
| `rep stosb` → video | the byte/word gap is the clearest single demonstration of a bus-limited machine |
| `fill_rect_m8` 80×200 | the real primitive, paying the two-bank row arithmetic. The gap against flat `stosw` is the per-row overhead section 7 assumes away |
| `rep movsw` RAM → video | section 2's MOVSW figure |
| `rep movsb` RAM → video | section 2's MOVSB figure, and the one `blit_rle` will pay for its RLE runs |
| `rep movsw` video → video | what a single-page fallback design would cost |
| `rep movsw` RAM → RAM | contention baseline |

Three details that matter for reading the output:

**Every run starts at the beginning of vertical retrace.** A 23 ms fill inside
a 16.7 ms frame straddles active display and blanking; without a fixed starting
phase the spread between repetitions would be noise rather than signal.

**Sizes are chosen to fit the timer, and shrunk if they do not.** The Zen timer
wraps at about 54.9 ms. A full-screen `MOVSB` copy is *predicted* at 73.7 ms,
so it would overflow even if the prediction is right. The harness starts each
primitive at a size that should fit and halves it until it does. Rows where the
size ended up below a full screen are marked `*` in the report: the per-byte
rate is measured, and the per-screen figure is that rate multiplied out.

**Do not touch the keyboard while it is running.** The PCjr scans the keyboard
from the non-maskable interrupt, which `CLI` cannot hold off, so a keypress
lands inside a measurement.

## Reading the output honestly

The program labels everything. **Measured** means it was timed on the machine
it ran on. **Predicted** means it is quoted from `DESIGN.md` section 2 and was
never measured by anybody. **Derived** means arithmetic on a measurement and no
new assumptions.

The one thing to be careful about:

> **An emulator cannot answer question 2.** Neither DOSBox nor DOSBox-X models
> the PCjr's memory contention. The Video Gate Array stealing bus cycles from
> the processor is the entire reason section 2's predicted throughput is as low
> as it is; without that, fills come out fast and the frame budget looks
> comfortable. Under emulation this program is a smoke test — it says the loops
> run, the page register behaves, the timer works and the flip is
> retrace-synced. Only a real PCjr settles whether section 7 is affordable.

`cycles=fixed 315` in the configs is a cycle budget, not a bus model. It gets
instruction timing into roughly the right territory for a 4.77 MHz 8088 and
does nothing at all about wait states.

Both reference repositories in `lib/repos/` say the same thing from experience:
Foster's `TODO.md` records real-hardware timings that differ from DOSBox by
enough to matter, and jrpiano documents a sound-gating bug that DOSBox does not
enforce, so a program that worked in the emulator was silent on hardware.

## Closing the gap: what has to happen on real hardware

M1 is not finished until this has been done on an actual PCjr with 128 KB and
an RGB monitor.

1. **Build it.** Install Open Watcom V2 and NASM, run `wmake`, and confirm
   `build\m1.exe` links.
2. **Smoke test it under DOSBox-X** with `conf/pcjr-128k.conf`. Expect the
   verification checks to pass and the timings to be optimistic.
3. **Run it on hardware**, `M1 /batch > M1.LOG`, and keep the log.
4. **Answer question 1** from the report's page verification section: are two
   distinct 16 KB pages available, does the `B8000` window track the CPU page
   field, and which BIOS register order is right.
5. **Answer question 2** from the measured `ns/byte` column against section 2's
   predictions. What matters is not whether the numbers match but whether
   section 7's budget still closes:

   - Section 7 budgets ~3,000 bytes of dirty-rect restore at ~7 ms and ~3,000
     bytes of sprite blits at ~8 ms, for ~26 ms while scrolling against a 50 ms
     frame at 20 Hz.
   - If the measured fill rate is materially worse than 680 KB/s, that budget
     shrinks and the design changes. Worth knowing before M3 builds a sprite
     engine on top of it.
   - The `fill_rect_m8` versus flat `stosw` gap is a second, independent thing
     to look at: it is per-row overhead the budget does not account for at all,
     and dirty-rect restores are made of small rectangles with many rows.
6. **Watch the visual test on a real RGB monitor.** Tearing and missed frames
   are the things emulators are least likely to reproduce faithfully, and the
   flip landing inside blanking is the one part of the design with no fallback.
7. **Try `/bios`** as well as the default. If the raw `OUT` path shows
   artefacts that the BIOS path does not, the address-mode bits in bits 6–7 of
   the page register are wrong, and that is a one-line fix worth finding now.

Record the results in this document, replacing the "Current status" section
above with the measurements.
