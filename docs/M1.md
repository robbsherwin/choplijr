# M1 — the video spike

`DESIGN.md` section 13 makes M1 a go/no-go gate, and it gates two things:

1. **Two 16 KB video pages in physical `00000`–`1FFFF` (port `0x3DF` pages
   0–7) on a jrIDE-class PCjr.** Sidecar RAM is not a hardware page.
   `DESIGN.md` requires 640 KB minimum and JrConfig's 32 KB video hole
   (`lib/repos/jrIDE/jrIDE.html`). If that hole cannot be had, page flipping
   is not free and section 7 changes. Section 14 is the fallback *after*
   JrConfig, not instead of it.
2. **Memory throughput.** Section 2 now has both the analysis table (~1500 /
   ~3500 / ~4600 ns/byte) and the hardware table from this log. Section 7's
   ~26 ms scrolling line is still analysis (sidecar-like fill). The measured
   video fill is 44.8 ms/screen.

So M1 does three things and stops: sets up mode 8 with two pages, flips them at
vertical retrace with visibly different content, and times the fill and copy
primitives with Abrash's Zen timer.

`Y:\github\open-watcom-v2` is the Watcom **source tree**, not the install.

## Building

```
wmake                     # -> build\m1.exe
wmake clean
```

From PowerShell, `wmake` does not like arguments that contain `=`. After
sourcing `setenv.ps1`, drive it through cmd:

```
cmd /c "wmake"
```

or pass NASM explicitly:

```
wmake NASM=lib\repos\nasm\nasm-3.02\nasm.exe
```

If `wmake` is the thing that is missing or misbehaving:

```
build.bat
```

`build.bat` runs the same three commands in the open and checks for each tool
before starting.

Both produce `build\m1.exe` plus NASM listings (`build\*.lst`) and a link map
(`build\m1.map`). The listings are worth keeping: this code cannot be run on
the machine it is written on, so reading the generated instruction stream is
the only review available before it reaches hardware.

`GROUND=BROWN` (default) or `GROUND=PINK` selects the IRGB value in palette
register 6. Clean first when changing it; the dependency graph does not know.

## Running

Two different runs, for two different questions. Do not substitute one for the
other.

### Attended visual — a human has to watch

This is the page-flip test. It is judged by eye (tearing, strobing, which page
is on the glass) and it only breaks early on a keypress. The ship machine is
jrIDE-class (sidecar). The 128 KB config is a historical smoke test and does
**not** `exit` when M1 returns:

```
wmake run-dev             # conf/pcjr-dev.conf — sidecar; closer to jrIDE
wmake run                 # conf/pcjr-128k.conf — historical 128 KB smoke test
```

What you will sit through, from `src/m1.c`, at 60 Hz vertical retrace:

| Phase | Default duration | Skip |
|---|---|---|
| Text: memory map, then a key to enter mode 8 | until a key (`/batch` skips the wait) | any key continues |
| Mode 8 verification, back to text, GO / NO-GO | brief | none |
| Identity flip | 360 frames = 6 s | any key |
| Smooth motion | 480 frames = 8 s (`/frames=N` to change) | any key |
| Key, then the timing loop | a few seconds; **do not touch the keyboard** | none — a keypress is an NMI |

Identity: green HUD vs red HUD, swapping twice a second, with a white block
jumping between low (page A) and high (page B). Motion: a white bar sweeping
left and right on a shared background. What a pass, a stuck page, a bank-math
stripe, a tear seam and a strobe look like is spelled out under "The visual
test" below.

`/nobench` skips the timing loop if you only want the pictures.

### `/nogfx` log — capture the report, skip the pictures

The visual test proves nothing to a redirected run: there is nobody to look
and nobody to press a key, so it would draw to an empty room for the whole of
its duration. `/nogfx` (same switch as `/noflip`) skips both visual phases.
`/batch` skips the "press a key" pauses. stdout is unbuffered from the first
character of `main` (`setbuf(stdout, NULL)`), so a log is not sitting in a C
runtime buffer if the process dies mid-run.

```
wmake run-batch           # conf/pcjr-128k-batch.conf: M1 /batch /nogfx > M1.LOG, then exit
```

That writes `build\M1.LOG` (the DOSBox `C:` mount is `build\`). Inside DOS:

```
M1 /batch /nogfx > M1.LOG
```

Redirecting DOSBox-X's *own* stdout on the Windows side is not the same thing
and will not capture the DOS program's report.

The report is 80 columns wide. A PCjr that booted into 40-column text will wrap
it, so either redirect to a file or run `MODE CO80` first.

### On real hardware

The same `build\m1.exe`. Attended visual as above, no extra flags. For a
timing log that is actually evidence for question 2:

```
M1 /batch /nogfx > M1.LOG
```

That is the run that can confirm or refute `DESIGN.md` section 2. An emulator
cannot.

### Options

| Option | Effect |
|---|---|
| `/nobench` | skip the timing runs |
| `/nogfx` | skip the visual page-flip test (`/noflip` is the same switch) |
| `/frames=N` | frames of the smooth-motion phase, default 480 (8 s at 60 Hz). Floor is 2. Identity stays 360 frames. |
| `/bios` | flip pages with `int 10h AX=0583h` instead of `OUT` to `0x3DF` |
| `/batch` | never wait for a keypress (use with `>` to capture a log) |
| `/reps=N` | timed repetitions per primitive, default 8 |
| `/pa=N` `/pb=N` | force two page numbers in 1–7. **Do not** use this to overlay DOS-occupied pages on jrIDE; that can trash the kernel. Page 0 is refused. |
| `/force` | run even where the BIOS model byte is not a PCjr's |

`/force` exists for emulator experiments and is genuinely unsafe anywhere
else: M1 writes to fixed physical addresses in the low 128 KB on the strength
of a page register only the PCjr has, and on any other machine those bytes
belong to DOS. Without `/force` the program checks `F000:FFFE` for `0xFD` and
refuses.

## What the program does, and why each part is there

### Source layout

```
src/pcjr.h           declarations and mode 8 constants
src/m1.c             the driver: memory map, verification, visual test,
                     benchmark harness, report
src/asm/pztimer.asm  Abrash's precision Zen timer, adapted to a segmented .EXE
src/asm/pcjrvid.asm  mode set, page register, palette, retrace waits
src/asm/prims.asm    fill_words / fill_bytes / copy_words / copy_bytes /
                     fill_rect_m8 / fill_band_m8
src/asm/dosmem.asm   DOS memory enquiry and allocation, far peek and poke
makefile             wmake build
build.bat            the same build without wmake
conf/                DOSBox-X configurations
```

The split follows section 12: logic in C, and only the routines where the
cycles actually live in assembly.

### 1. Where is the memory?

M1 does not assume the plan in section 3 works. It reports:

- `int 12h` memory size, and what it means. jrIDE BIOS sets this to **736 KB**
  (`jrIDE.html`). A 128 KB PCjr should say **112 KB**. The product floor is
  **640 KB** after a 32 KB video reserve.
- The whole DOS memory arena, walked through the MCB chain
  (`int 21h AH=52h`), block by block, with each block's physical span and
  whether we own it.
- Which of the eight 16 KB pages (0–7 = first 128 KB, the only `0x3DF`
  targets) are usable: claimed from DOS, above the arena (classic BIOS
  withhold), an MCB hole, or **JrConfig's `/V` window**. JrConfig 3.10 stores
  the size at `JRCONSYS+77h` and the start page at `+76h` (follows `/S`).
  Without `/S`: `/V16` at `1C00h`, `/V32` at `1800h`, `/V64` at `1000h`. That
  window may still sit inside owner `0008`. Page 0 is never used. The current
  CRT page is marked. A huge free block above `0x1FFFF` is *not* a video page.

Then it claims the largest free block DOS will give up (scratch / sidecar
workspace) and picks the highest two usable pages in 1–7 — pages 6 and 7
when JrConfig's window is `/V32` at `1800h` or `/V64` at `1000h`.

### 2. Verification, before anything is built on top

Three checks, all done in mode 8, all reported as pass or fail:

- **The two pages are distinct RAM.** Signatures written to the first and last
  word of each page and read back. On a machine where the address decode wraps,
  both "pages" would be the same memory, and the flip would appear to work
  while doing nothing at all.
- **The B8000 window follows the CPU page field.** Section 3 states as fact
  that the PCjr has no separate video RAM and that `B800:0000` is a window onto
  whichever 16 KB block the CPU page field selects. M1 writes through the
  window, reads back from the physical address, and then does it the other way
  round.
- **Which of `BH` and `BL` `int 10h AX=0583h` wants as the CPU page.** Section 3
  says `BX = (cpu << 8) | crt`. Flashparty's `set_vid_160_100_16` implies the
  opposite, and Ralf Brown agrees with Flashparty. Rather than pick a side, M1
  puts a distinct signature in each page, asks BIOS for a specific pairing, and
  reports which one turned up in the window.

If any of the first two fails, M1 stops and says NO-GO, because the benchmarks
below would otherwise be measuring something other than what they claim.

### 3. The visual test

Two phases, and the second is the interesting one. Both are skipped by
`/nogfx`. Both break early on any keypress. Defaults are named constants in
`src/m1.c`: `IDENTITY_FRAMES` 360 (6 s at 60 Hz), `IDENTITY_SWAP_FRAMES` 30
(a swap twice a second), `MOTION_FRAMES_DEF` 480 (8 s). `/frames=N` changes
only the motion phase.

**Page identity.** Page A: green HUD band (palette index 2) and a white block
low on the screen (byte column 30, rows 130–153). Page B: red HUD band (index
4) and a white block high (same column, rows 40–63). The CRT page field swaps
twice a second; the CPU window is pointed at the page that is *not* showing.
Drawing is by physical segment, so this phase is a test of the CRT page field,
not of the `B8000` aperture (that was the verification step).

- **PASS:** the top band alternates green / red twice a second and the white
  block jumps between low and high with it.
- **Stuck / wrong CRT page:** the picture never changes. Same symptom if the
  two pages were the same RAM — but verification should have stopped with
  NO-GO before you got here.
- **Bank-math stripe:** `fill_rect_m8` walks even scanlines in the first 8 KB
  and odd scanlines in the second. If that walk is wrong, the "solid" HUD
  bands and the white block are venetian-blinded: every other scanline is the
  wrong colour, or the block is split across the two banks instead of sitting
  as a rectangle.

**Smooth motion.** Identical backgrounds on both pages (grey HUD, index 7),
and a white bar eight pixels wide swept across rows 28–127 — redrawn into the
back page every frame, with its previous position restored from the band
model first. That is a one-object version of the per-buffer dirty-rect
pipeline in section 7.

- **PASS:** the bar travels smoothly left and right, no horizontal seam, no
  strobe.
- **Tear seam:** a horizontal break across the bar. The flip landed outside
  vertical blanking.
- **Strobe:** the bar flashes or jumps rather than ticking one step per
  retrace. A frame was missed.

Both phases paint the sky, mountain strip and ground as flat horizontal bands
in the section 5 palette indices. That is not decoration. A solid horizontal
band is scroll-invariant, which is the observation section 7's whole budget
rests on, so it is the right thing for the spike to be drawing. The bottom 25
rows are the build-time ground colour (`GROUND=BROWN` or `GROUND=PINK`) under
a yellow highlight row — the open question in section 5, only meaningful on
the RGB monitor.

### 4. The benchmarks

Nine primitives, timed with the Zen timer, interrupts disabled, the display
active in mode 8 and the writes going to the page the CRTC is not showing —
which is the situation the renderer will actually be in.

| What | Why it is in the list |
|---|---|
| `rep stosw` → video via `B8000` | section 2's fill figure, through the window |
| `rep stosw` → video, direct segment | the same fill addressed as plain RAM. Identical on paper; a difference would be very interesting |
| `rep stosw` → plain RAM | the same fill somewhere the video gate array is not fetching from, which isolates contention from instruction cost |
| `rep stosb` → video | the byte/word gap is the clearest single demonstration of a bus-limited machine |
| `fill_rect_m8` 80×200 | the real primitive, paying the two-bank row arithmetic. The gap against flat `stosw` is the per-row overhead section 7 assumes away |
| `rep movsw` RAM → video | section 2's MOVSW figure |
| `rep movsb` RAM → video | section 2's MOVSB figure, and the one `blit_rle` will pay for its RLE runs |
| `rep movsw` video → video | what a single-page fallback design would cost |
| `rep movsw` RAM → RAM | contention baseline |

Three details that matter for reading the output:

**Every run starts at the beginning of vertical retrace.** A 23 ms fill inside
a 16.7 ms frame straddles active display and blanking; without a fixed starting
phase the spread between repetitions would be noise rather than signal.

**Sizes are chosen to fit the timer, and shrunk if they do not.** The Zen timer
wraps at about 54.9 ms. A full-screen `MOVSB` copy is *predicted* at 73.7 ms,
so it would overflow even if the prediction is right. The harness starts each
primitive at a size that should fit and halves it until it does. Rows where the
size ended up below a full screen are marked `*` in the report: the per-byte
rate is measured, and the per-screen figure is that rate multiplied out.

**Do not touch the keyboard while it is running.** The PCjr scans the keyboard
from the non-maskable interrupt, which `CLI` cannot hold off, so a keypress
lands inside a measurement.

## Reading the output honestly

The program labels everything. **Measured** means it was timed on the machine
it ran on. **Predicted** means it is quoted from `DESIGN.md` section 2 and was
never measured by anybody. **Derived** means arithmetic on a measurement and no
new assumptions.

The one thing to be careful about:

> **An emulator cannot answer question 2.** Neither DOSBox nor DOSBox-X models
> the PCjr's memory contention. The Video Gate Array stealing bus cycles from
> the processor is the entire reason section 2's predicted throughput is as low
> as it is; without that, fills come out fast and the frame budget looks
> comfortable. Under emulation this program is a smoke test — it says the loops
> run, the page register behaves, the timer works and the flip is
> retrace-synced. Only a real PCjr settles whether section 7 is affordable.

`cycles=fixed 315` in the configs is a cycle budget, not a bus model. It gets
instruction timing into roughly the right territory for a 4.77 MHz 8088 and
does nothing at all about wait states.

Both reference repositories in `lib/repos/` say the same thing from experience:
Foster's `TODO.md` records real-hardware timings that differ from DOSBox by
enough to matter, and jrpiano documents a sound-gating bug that DOSBox does not
enforce, so a program that worked in the emulator was silent on hardware.

## What hardware showed

Question 1 is **yes**: two distinct 16 KB pages in 0–7, `B8000` tracks the CPU
page field, BIOS `BL` = CPU page. JrConfig `/V64` at `1000h` is inside owner
`0008`; M1 treats that window as the video reserve and picks pages **6 and
7**. Do not `/pa` a DOS-occupied page.

Question 2 is answered by the table in Current status. The analysis fill rate
(~1500 ns/byte, ~23.5 ms/screen) is what sidecar RAM does. Video RAM is 2803
ns/byte, 44.8 ms/screen. `fill_rect_m8` is 2935 ns/byte (46.9 ms/screen) —
close to flat video `stosw`, so per-row overhead is small on a full-screen
rect. RAM→video `movsb` (what `blit_rle` will pay) is 4515 ns/byte, 72.2
ms/screen. Video→video `movsw` is 80.8 ms/screen: a copy-bound single-page
fallback does not fit a 50 ms frame.

Section 7's ~26 ms scrolling total stays analysis. It used the sidecar-like
rate. The design that still fits is the one already written: dirty rects, no
full-screen copy, scroll-invariant bands. DOSBox-X remains a smoke test only.
