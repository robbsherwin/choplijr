4. **Reuse.** M9 presentation, M8 sound, JrConfig pages, `blit_rle`,

5. **Fixed: stuck burning-house ghost pixels.** Found on attended play, not
   the pad benchmark (which never gets near a barracks): fly past the first
   barracks and back, and a fragment of the flame overlay stays lit where it
   has no business being — inside the sky-haze dither band, since the flame
   sprite's row span (`world_to_sy(HOUSE_WORLD_Y+4)`, 5 rows tall) sits
   entirely inside it. Cause: `house_fire_00_e`/`_01_e` don't share the same
   opaque silhouette frame to frame, so RLE transparency (skip, don't touch
   dest) can't erase a pixel the *other* frame lit — that only happens via a
   background restore, and the flame's static-camera redraw path (triggered
   by its animation timer or `flag_changed`, independent of scrolling) drew
   straight over the old frame with no restore first, and no dirty-rect
   tracking to ever schedule one. Fixed in `src/m10.c`'s static-camera
   `draw_scenery` call: it now tracks into `scenery_mark[back]` instead of
   passing no list, so the next scroll's restore pass erases it. Same class
   of bug would have hit the base flag's flicker (`flag_changed`) too, same
   fix. **Confirmed by eye (2026-09-10) on a second repro this fix did not
   cover: a sortie transition**, not the original within-sortie case —
   dying and starting the next sortie left both the burning house *and* a
   tank still on screen at the old scroll position. A first attempt reset
   the same per-page trackers `run_viewer()`'s own setup resets
   (`scenery_mark[]`, `scenery_full[]`/`scenery_invalidate()`,
   `last_fire_bit[]`, `last_flag_bit[]`, `lists[]`) — verified zero
   regression on the pad benchmark, but the tank was still there by eye,
   because the actual cause is broader than any one tracker: the dirty-rect
   system only knows how to erase what a sprite's *own* dirty rect says
   changed, and has no notion of "the whole scene just changed." Once
   `scroll_x` jumps discontinuously to `SCROLL_START`, whatever was drawn
   at the old position — burning house, tank, anything — has no dirty rect
   pointing at it any more and is never scheduled for a restore. It just
   sits there, regardless of which trackers got reset.

   **Fixed properly**: `next_sortie()` now calls `paint_world(seg_a)` /
   `paint_world(seg_b)`, the same full background repaint (sky, mountain
   placeholder, ground — unconditional fills covering every row) that
   `run_viewer()`'s own setup already does once before its loop begins.
   This wipes every sprite pixel on both pages regardless of what tracked
   it, and `scenery_invalidate()` (kept from the first attempt) forces a
   full houses/fence/base redraw on the very next present so the new
   scene draws back in on top of the clean background — matching exactly
   what a fresh game's first tick already does. One full-screen fill on
   each page, once, at a sortie boundary the player is not interacting
   with anyway (still inside the death animation / banner pause) — not a
   per-tick cost. Verified zero regression on the pad benchmark (identical
   byte counts and BIOS-tick count). **Confirmed by eye (2026-09-10): both
   the barracks and the tank are gone on the next sortie.**
6. **Fixed: chopper mid-turn frames used the same art for both turn
   directions.** Found on attended play: turning left, the frame closest
   to a full turn visibly showed the right-turn art instead. Cause:
   `draw_chopper()` (`src/m10.c`) only ever built a mirrored image for the
   full side view (`abs_t == 5`, pre-rendered `chopper_side_fe`/`_fo` plus
   a `flip` flag) — every mid-turn frame (`abs_t` 0-4, `chopper_head_e`)
   drew the same sprite regardless of direction, because no mirrored
   `chopper_head_fe`/`_fo` asset existed. The original doesn't need one:
   it renders one bitmap through a real-time signed shear
   (`chooseChopperSprite`/`jumpSetSpriteTilt`, choplifter.s) that leans the
   opposite way when facing left; this port pre-renders instead, so the
   mirror needs its own baked copy per frame. Fixed at the source: `tools/
   build_sprites.py`'s `emit_flip` gate, previously hardcoded to
   `chopper_side` only, now also covers `chopper_head` (the flipped RLE
   was already computed for every sprite, just never emitted for this
   group) — regenerated `src/sprdata_rle.c` from `lib/repos/
   ChoplifterReverse/CHOPGFX` through the existing pipeline, no new art
   authored by hand. `draw_chopper()` now carries a flip-pair (`bfe`/`bfo`)
   alongside the normal pair for both the side and head-on branches and
   picks between them the same way for either. Scope: the chopper body
   only, not the rotor disc (still drawn unflipped in the head-on case,
   same as before — not reported as visibly wrong).

   The new sprite data (10 arrays, ~1.5 KB) pushed `m10.exe`'s small-model
   DGROUP over the 64 KB cap by 480 bytes on the first attempt. Recovered
   headroom two ways, both zero-risk: removed `chop_view_e`/`chop_view_o`/
   `chop_view_count` (confirmed, by grep across all of `src/`, dead code
   with no reader anywhere — an unused leftover the generator had been
   emitting into both `sprdata.c` and `sprdata_rle.c` all along) from the
   generator; and trimmed `usage()`'s control/gameplay paragraph, which
   duplicated content already in `docs/M5.md`/`docs/M10.md`, down to a
   short pointer. Margin: 528 bytes free of 64 KB after this fix (was
   1,056 before it) — comfortably clear of the ~128-224 byte range that
   caused a real crash earlier this session (`CLAUDE-THOUGHTS.md`'s DGROUP
   entry), but still worth re-checking before the next static-data
   addition (palette-effect tuning, item 3, is the next one in line).
   Verified zero byte-count regression on the pad benchmark. **Confirmed
   by eye (2026-09-10): the mirror looks right in play.**
7. **Fixed: barracks fire-frame artifacts on rapid direction reversal.**
   Reported on attended play: quickly moving left and right near a
   barracks leaves a stale flame fragment. Same underlying cause as item
   5's ghost-pixel fix (`house_fire_00_e`/`_01_e` don't share an opaque
   silhouette, so RLE transparency can't erase the old frame — only a
   background restore can) but a different trigger: house 3 starts
   burning from sortie 1 (`next_sortie`/`init_hostages`), and its flame
   frame flips every 4 sim ticks (`draw_houses`' `fire_bit`) regardless of
   whether the camera moves. Item 5's fix only restores that footprint on
   the *next real scroll* — fine when flying past once, but when the
   camera barely moves (hovering / reversing direction rapidly near the
   barracks, via the scroll lead-window's deadzone), several flame flips
   can stack up unrestored before scrolling resumes.

   Fixed in `run_viewer()`: when a house is burning (`any_house_burning()`,
   a cheap 4-iteration check, `N_HOUSES`) and the fire-bit is about to
   flip for this page, restore `scenery_mark[back]`'s already-tracked
   flame footprint on that same tick — independent of `full_sc`, so this
   does *not* force the much bigger unconditional redraw of every
   house/fence/base `full_sc` triggers on an actual scroll. That distinction
   mattered here: a first attempt tied this to `full_sc` directly and, because
   a house is burning for most of a normal game, turned into a full scenery
   redraw every 4 ticks almost the whole time — a real regression, caught by
   the pad-benchmark byte-count check (`rle blit` 859→913, `mountain`
   126→168, `scenery` 167→179) before it shipped. The corrected version
   restores only the tracked flame footprint; `rle blit`/`mountain`/`scenery`
   are back to exact baseline, and `restore` carries only the new fix's own
   necessary cost (872→1089 avg on the pad benchmark, where house 3's flame
   is always burning) — the price of actually erasing the stale pixels, not
   of redrawing anything extra. **Confirmed by eye (2026-09-10): the
   artifact is gone.**
8. **Alien/saucer shot made visible.** Reported on attended play: the
   alien's projectile (killed the player without an obvious visible cause)
   was a tiny 2x2 grey/orange dot (`SHELL_PX`/`SHELL_C_GREY`/`_ORANGE`) —
   the same sprite and type (`ET_SHELL`) tank shells use, sized for the
   original Apple II display. New `ET_ALIEN_SHOT` entity type: identical
   physics and collision to `ET_SHELL` (both generic over entity geometry,
   not type — `update_shell`, `ordinance_check` needed no changes), so tank
   shell difficulty/hitbox is untouched, but its own rendering: a
   procedural 4x4 filled square (`draw_solid_square`, `src/m10.c`, mirrors
   `blit_at`'s own clip/dirty-rect math since a `plot_px` loop has no other
   way to register what it touched) that fades from light red (index 12)
   to dark red (index 4) once `e->ground - chop_ground` — already growing
   every tick from `ent_basic_phys`'s existing ground-drift, no new
   `entity_t` field needed — passes a fixed threshold (~8 ticks/0.4 s into
   the shot's flight). Zero new DGROUP cost (no new static data).
   **Confirmed by eye (2026-09-10).**
9. **Mountain band removed from M10.** Requested after play: the flat
   4-tile grey ridge (no peaks) never read as camera motion, and it was
   genuinely expensive — the combat-window capture (`M10-05.LOG`) measured
   `mountain` at 28.2% of `present`, ~17% of the *entire* frame budget, by
   itself the single largest cost this session found anywhere in the
   pipeline. Removed `mountain_shift`/`draw_mountains`/`draw_mountains_dirty`
   from `src/m10.c` along with their call sites in `run_viewer()` (and the
   now-dead `last_shift[]`/`shift`/`old_sc` state, plus `restore_list`'s
   `band_hit` return value, which existed solely to decide when to retile
   the ridge) and `blit_mtn_fast` from `src/asm/blit.asm` and `pcjr.h`
   (the fast-path helper written for `draw_mountains` earlier this session
   — genuinely dead now, not left as an orphaned "just in case").
   `mountain_e`/`mountain_o` (`src/sprdata_world.c`) and
   `tools/build_sprites.py`'s mountain tile generation were deliberately
   **left alone**: `sprdata_world.c` is shared by every milestone back to
   M4, all of which still draw their own mountain band from that same
   data — removing it would have broken `m4.exe` through `m9.exe`. Only
   M10's own copy of the logic came out; a full `wmake` confirms all ten
   milestones still build.

   `band_solid()` already treats `MOUNTAIN_ROW`'s 4-row span as a plain
   solid-8 band for restore purposes (same as the sky/ground bands), so
   nothing else needed to change: the band still shows as a flat dark-grey
   strip (`paint_world`'s original fill), correctly restored by the
   generic dirty-rect system whenever anything crosses it. Verified on the
   static pad benchmark: `mountain` phase and byte count both read exactly
   0; every other WORKSET number (`restore`/`scenery`/`sprites`) is
   unchanged from the pre-removal baseline, and `rle blit` dropped by
   exactly the amount `mountain` used to contribute to it (859→764 avg).
   DGROUP unaffected (mountain sprite bytes still physically link into
   `m10.exe` via the shared `sprdata_world.obj`, just unreferenced by
   M10's own code — OMF/`wlink` has no per-symbol dead-stripping, so this
   didn't reclaim margin, but wasn't expected to). Total BIOS ticks on the
   static pad dropped 68→64 even without real scrolling.

   **Confirmed in a real attended flight, `docs/claude-logs/M10-06.LOG`**
   (583 sim ticks, 336 scrolling — a much richer sample than the static
   pad): `mountain` is 3 of 1300 BIOS ticks (0.4% of `present`, down from
   28.2% in `M10-05.LOG`) — that residual is just the two `bios_ticks()`
   calls bracketing an now-empty block, not real work, exactly the
   "standing check it stays near 0" the brackets were kept for. Byte count
   is exactly 0. `present`'s own share of the whole frame dropped (60.4%→
   56.5%) and `idle`'s grew (24.1%→26.9%) — less work per tick, more slack
   waiting on retrace. Not a controlled A/B (different flight, keyboard vs
   joystick control), so no single "+X%" headline number, but the removal
   mechanism is confirmed exactly as predicted.

   Discussed as a first step before deciding what replaces the motion cue
   (candidates raised: slow-parallax stars, or scoping a peaked mountain to
   just the pre-`FIRST_HOUSE_X` approach corridor) — neither implemented
   yet.

Ground colour stays BROWN. Video `stosw` is 44.8 ms/screen on hardware (M1);
the sim loop never fills a page.

have measured on its own.

## Building

Same toolchain as [docs/M1.md](M1.md). From PowerShell:

```
. .\setenv.ps1
cmd /c "wmake NASM=lib\repos\nasm\nasm-3.02\nasm.exe"
```

That builds `build\m1.exe` through `build\m10.exe`. There is no `wmake run-m10`;
do not launch DOSBox from the makefile for this visual.

`GROUND=BROWN` (default) or `GROUND=PINK`. Clean first when changing it.

## Hardware pass

A human has to watch **and listen**. Copy `build\m10.exe` to the PCjr the
same way as M1 (`J:\GAMES\CHOPLIJR\` on the last GO). JrConfig
`DEVICE=JRCONFIG.SYS /V64 /L`, pages 6 and 7. RGB monitor.

Escape hatch is **Esc** (title or logos → DOS, play → DOS). Do not start
an emulator until someone is in front of it; the hardware run is the one
that fills this list.

Do not redirect M10 over `M1.LOG`. The M1 GO rates are in `DESIGN.md`
section 2; that filename is for an M1 re-run if you ever want a new
throughput file. For a combat-window `/phases` capture, drop `/batch` and
`/ztimer` (attended, no fixed frame count) and fly into a fight before Esc.
`/force` is an emulator-only flag (bypasses the BIOS model-byte check
DOSBox-X fails) and is not needed on real hardware:

```
M10 /phases > M10-COMBAT.LOG
```

`/force` only on an emulator whose model byte is not `FDh`. Emulator
`M10.LOG` is not the hardware log.

Use `conf/pcjr-128k-m10.conf` (`m10.exe /force`) only as a smoke test of
the counters and the `/ztimer` path.

Emulator audio and frame times are a smoke test only.
